## Почему так

Проект сознательно без собственного backend-сервера: весь продукт — это
статическая страница плюс Supabase как managed backend-as-a-service
(БД + авторизация + файлы + автогенерируемый REST API). Это
радикально снижает сложность эксплуатации (ничего не падает на
сервере, нечего чинить кроме статики и настроек Supabase), но означает,
что:

- любая бизнес-логика, которая обычно живёт на backend (валидация,
  права доступа), здесь либо на клиенте (валидация форм — слабая,
  не доверенная), либо в Supabase RLS (права доступа — настоящая
  граница безопасности);
- нет промежуточного API-контракта — frontend обращается к таблицам
  Postgres напрямую через PostgREST, так что имена колонок в БД — это,
  по сути, и есть публичный API.

## Поток данных: отображение каталога покупателю

1. При открытии `index.html` сразу читается кэш каталога из
   `localStorage` (`podium_lamps_cache_v1`), если есть и не истёк
   (TTL 5 минут) — показывается мгновенно.
2. Параллельно запускается `fetchLamps()`:
   - сначала `fetchLampsDirect()` — прямой запрос к
     `Supabase REST API` (`GET /rest/v1/lamps`) с таймаутом 6 секунд;
   - если не успел/упал — `fetchLampsFallback()`, запрос к
     `/lamps.json` на том же домене (`podium-sale.ru`), без таймаута
     (тот же сервер, что и сам сайт — не подвержен проблемам
     доступа к иностранным хостам).
3. Полученные строки проходят `mapRows()` (переименование полей под
   UI-модель) и сохраняются обратно в `localStorage`.
4. Параллельно так же (с тем же fallback-паттерном в целом, но проще
   — без fallback-файла, своя логика в `fetchRate()`) подтягивается
   курс евро→рубль из `public.settings`.
5. `render()` строит карточки на основе текущих фильтров/страницы;
   `formatPrice()` переводит цену в рубли на лету при каждом рендере.

## Поток данных: редактирование каталога сотрудником

1. Сотрудник логинится в `admin.html` через Supabase Auth.
2. `loadLamps()` читает всю таблицу `lamps` (авторизованным запросом,
   но чтение разрешено и анонимно — таблица одна и та же).
3. Добавление/редактирование светильника — прямой
   `sb.from('lamps').insert(...)`/`.update(...)` (авторизованный
   запрос, разрешённый RLS только для роли `authenticated`).
4. Фото загружается в Supabase Storage bucket `lamp-images`, публичная
   ссылка сохраняется в поле `image`.
5. Любое изменение в `lamps` в Supabase мгновенно видно и на витрине
   при следующей загрузке/обновлении каталога (учитывая 5-минутный
   кэш на клиенте витрины) — никакого редеплоя не требуется.

## Поток данных: резервная копия `lamps.json`

1. GitHub Actions по расписанию (каждые 5 минут, `cron: '*/5 * * * *'`,
   плюс ручной запуск `workflow_dispatch`) выполняет
   `GET /rest/v1/lamps?select=*&order=sort_order.asc` с анонимным
   ключом, сохраняет результат как `lamps.json`.
2. Если файл изменился — коммитит и пушит в `main` от имени
   `catalog-sync-bot`.
3. Push в `main` триггерит автодеплой Timeweb — обновлённый
   `lamps.json` становится доступен по `podium-sale.ru/lamps.json` в
   течение ~30 секунд после коммита.

Статус на момент написания: подтверждено рабочим по истории коммитов
(`git log` содержит регулярные коммиты `Auto-sync catalog`).

## Границы безопасности

- Границу «кто может читать/писать» определяет **исключительно RLS
  в Supabase** (настраивается в дашборде Supabase, не в коде
  репозитория). Анонимный ключ в коде — не секрет, он публичен по
  дизайну Supabase.
- `admin.html` отдаётся как обычная статика — её URL не скрыт
  (`<meta name="robots" content="noindex, nofollow">` только убирает
  её из поисковой выдачи, не ограничивает доступ). Защита входа —
  исключительно через необходимость пройти Supabase Auth, чтобы что-то
  изменить.
