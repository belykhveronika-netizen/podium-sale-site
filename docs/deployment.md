# Деплой

## Продакшн

**https://podium-sale.ru**

## Хостинг: Timeweb App Platform

- Подключён к GitHub-репозиторию
  `belykhveronika-netizen/podium-sale-site` через встроенную
  GitHub-интеграцию Timeweb.
- Автодеплой при каждом push в ветку `main`, занимает ~15–30 секунд.
- Раздаёт статические файлы как есть — никакой серверной
  конфигурации/переменных окружения на стороне Timeweb не
  задокументировано как используемое.
- Домен `podium-sale.ru` привязан к этому Timeweb-приложению (NS
  делегированы на `ns1-4.timeweb.ru`/`.org` по данным на момент
  последней проверки).

## Известные неясности — проверить перед изменением деплоя

В комментарии в `app.js` (блок витрины каталога) есть ссылка:

```
https://podium-rasprodazha-belykhveronika-5974s-projects.vercel.app/admin.html
```

Это указывает на то, что в какой-то момент разработки существовал
(или всё ещё существует) параллельный деплой на **Vercel**
(проект `podium-rasprodazha`, аккаунт
`belykhveronika-5974s-projects`) с доменом `podium-sale.ru`,
добавленным туда же. Из репозитория невозможно достоверно определить,
актуален ли сейчас этот Vercel-деплой или это остаточный след более
раннего этапа разработки, когда хостинг ещё не был окончательно
перенесён на Timeweb.

**Перед любыми изменениями в деплое или DNS** нужно:
1. Проверить в аккаунте Vercel (`belykhveronika-5974s-projects`),
   существует ли ещё проект `podium-rasprodazha` и привязан ли к нему
   домен `podium-sale.ru`.
2. Проверить фактические NS-записи домена `podium-sale.ru` у
   регистратора — на какой хостинг они указывают прямо сейчас.
3. Если Vercel-проект больше не используется — обновить комментарий в
   `app.js`, указывающий на него, чтобы не вводить в заблуждение
   следующего разработчика.
4. Если Vercel всё ещё активен параллельно с Timeweb — задокументировать
   здесь, что именно на нём разворачивается и зачем (например, только
   staging/preview для админки).

Это не было уточнено в рамках текущей задачи резервного
копирования/handoff — пометка оставлена намеренно, чтобы не потерять
этот открытый вопрос.

## GitHub Actions — автосинхронизация каталога

`.github/workflows/sync-catalog.yml`:

- Триггеры: `cron: '*/5 * * * *'` (каждые 5 минут) и
  `workflow_dispatch` (ручной запуск из вкладки Actions).
- Нужные права: `permissions: contents: write` (уже выставлено в
  workflow) — чтобы бот `catalog-sync-bot` мог коммитить в `main`.
- Делает `curl` к Supabase REST API с анонимным ключом (сейчас
  прописан прямо в YAML как `env:`, см. раздел ниже про секреты),
  сохраняет ответ как `lamps.json`, коммитит и пушит, если файл
  изменился.
- Статус: подтверждено рабочим по истории git-коммитов (регулярные
  `Auto-sync catalog`). Если коммитов с этим сообщением давно не было
  — первым делом проверить вкладку **Actions** в GitHub на предмет
  упавших запусков.

### О ключе Supabase внутри workflow-файла

`SUPABASE_URL` и `SUPABASE_ANON_KEY` в `sync-catalog.yml` прописаны
как открытый текст прямо в YAML, а не вынесены в GitHub Secrets. Это
тот же публичный анонимный ключ, что используется и в `app.js`/
`admin.html` — по дизайну Supabase он не является секретом
(безопасность обеспечивает RLS, а не секретность ключа), поэтому
практического риска это не несёт. Тем не менее, хорошей практикой
было бы вынести эти значения в `Settings → Secrets and variables →
Actions` репозитория — это не сделано в рамках текущей задачи, чтобы
не трогать рабочий workflow без необходимости (см. явное требование
"не удаляй и не перезаписывай рабочую функциональность").

## Ручной откат

Поскольку деплой — это просто "раздать файлы из `main`", откат —
это `git revert` нужного коммита (или `git reset`/force-push, если
осознанно принято такое решение) и обычный push — Timeweb подхватит
предыдущую версию тем же автодеплоем.
